# Polymarket天気市場研究・New Yorkベースライン設計

## 目的

この研究では、New Yorkの日最高気温を対象に、各取引時点で取得可能だった気象情報からPolymarketの特定バケットが決済される確率を推定し、Polymarketの実行可能価格と比較する。目標は単なる気温の的中率ではなく、手数料・スリッページ・不確実性バッファを含めた後にも再現性のある正の期待値が残るかを判定することである。

初回成果物は、実データを使った市場ルール解析、Point-in-Timeデータセット、GEFSベースライン確率、理論および簡易約定バックテスト、検証レポートである。L2板の完全な再生、機械学習、Forward Test、Paper Trading、実取引は後続フェーズとし、この段階では注文を送信しない。

## 採用する構成

研究ルートは `weather-polymarket-research/` とする。収集器は外部サービスから取得した応答を `data/raw/` に保存し、正規化処理は市場・予報・観測・価格を共通のUTC時刻と対象日の識別子へ変換する。モデル層は市場価格を使わないWeather Onlyモデルを主結果とし、市場価格を特徴量にしたモデルは将来の比較用に分離する。バックテスト層は、観測された約定価格を使う理論版と、ask・スプレッド・スリッページを加えた簡易実行版を別々に計算する。

各レコードには少なくとも `source`、`market_id`、`station_id`、`target_date`、`forecast_issue_time`、`forecast_valid_time`、`received_time`、`trade_time`、`resolution_time` を保持する。取引候補は `forecast_issue_time <= trade_time`、`received_time <= trade_time`、`market_price_timestamp <= trade_time` を満たす情報だけで作る。条件を満たさないレコードは除外し、除外数をデータセットマニフェストに記録する。

## 外部データの役割

PolymarketのGamma APIは市場・イベント・説明文・ルール・トークン識別子の取得に使う。CLOB APIは価格、スプレッド、価格履歴などの市場データに使う。市場メタデータと価格履歴を別の取得物として保存し、後からどの価格をどのルールに紐づけたかを追跡できるようにする。公式ドキュメントは `https://docs.polymarket.com/api-reference/introduction` と `https://docs.polymarket.com/api-reference/markets/get-batch-prices-history` を参照する。

GEFSは予報の主データ源とする。まず利用可能な履歴アーカイブまたは公開された格子データを調査し、対象時点の予報発行時刻を保持できる場合だけバックテストに使う。NOMADSのGEFSデータサーバーは候補の一次データ源であり、`https://nomads.ncep.noaa.gov/dods/gefs/` を起点に取得可能期間と変数を確認する。履歴予報を再構成できない場合に、現在の予報や後日修正された値で穴埋めしてはならない。

観測値は、決済ルールが指定する観測所を優先し、METAR/SPECIまたは同等の公式観測資料から取得する。NCEIのMETAR資料は航空観測所の観測であることを明示しているため、都市名だけで観測所を推測しない。観測所の識別子、タイムゾーン、日界、丸め、欠測、訂正報告を市場ルールと併せて保存する。

参照実装として `yangyuan-zhen/PolyWeather` と `suislanchez/polymarket-kalshi-weather-bot` を読むが、参照実装の現在値や取引成績を研究結果として転載しない。前者は都市・観測所・決済値の対応を、後者は31メンバーのアンサンブル比率を確認するために使う。

## 市場ルールの安全境界

市場説明文から抽出したルールは、構造化データとして保存した後に必ず規則ベースで検証する。最低限、都市、観測所、対象日、タイムゾーン、測定対象、下限、上限、境界の開閉、決済ソースが欠けていないことを確認する。曖昧な説明、複数の候補観測所、範囲境界を確定できない市場は `invalid_market_rule` としてバックテストから除外する。

LLMや外部ライブラリを市場ルールの最終決定者にしない。ルールの確定根拠は、保存した説明文、公式ルール、観測所マッピング、抽出結果の検証ログである。

## 確率モデルと取引条件

最初のモデルは次の順序で実装する。

1. `Market Baseline`：市場のaskまたはmidを確率の代理値として記録する。
2. `GEFS Ensemble Ratio`：対象バケットに入るメンバー数を有効メンバー数で割る。
3. `Gaussian Ensemble`：GEFSメンバーの平均と標準偏差から正規分布を近似し、バケットの区間確率を求める。

バケットは市場ルールの境界に従って評価し、端点の扱いを暗黙に丸めない。欠測メンバーを失敗したメンバーとして数えず、有効メンバー数を分母にする。有効メンバーがゼロの場合は予測を作らず `insufficient_data` とする。

取引候補の基本計算は以下とする。

    gross_edge = model_probability - observed_ask
    executable_price = min(1.0, observed_ask + assumed_spread + assumed_slippage)
    net_edge = model_probability - executable_price - trading_fee - uncertainty_buffer

初期設定は、仮定スプレッド0.01、仮定スリッページ0.01、不確実性バッファ0.02、最小エッジ0.08とする。設定値は結果に埋め込む。価格や手数料がない場合にゼロを暗黙に代入せず、その試行を `insufficient_data` とする。

## バックテストと評価

バックテストはイベント単位で、シグナル時刻、モデル確率、価格、実行価格、結果、ポジションサイズ、総損益、純損益を保存する。Level 1は観測価格だけを使い、Level 2はask、スプレッド、スリッページ、取引手数料を使う。L2注文板の再生はこの設計の受け入れ条件に含めない。

予測評価はバケットのBrier Score、Log Loss、校正誤差を中心にし、気温値を再構成できるデータが揃った場合にMAE、RMSE、CRPSを追加する。取引評価はGross PnL、Net PnL、ROI、Win Rate、Average/Median Edge、Sharpe-like metric、最大ドローダウン、最大連敗数を出す。結果は全体、対象日、リードタイム、価格帯、エッジ帯に分割できる形式にする。

データが空、期間が不足、予報履歴が時点整合しない、観測所または市場ルールを確定できない場合は、ゼロ損益の成功として扱わない。`status` は `success`、`insufficient_data`、`invalid_market_rule`、`collection_error` のいずれかとし、理由、対象期間、取得件数、除外件数を `results/dataset_manifest.json` と `results/backtest_summary.json` に保存する。

## 受け入れ条件

研究ディレクトリでテストコマンドを実行すると、時点リークのある予報が除外され、境界付きバケット確率が合計1になり、実行価格と純エッジが設定どおり計算される。実データ収集コマンドは再実行可能で、取得済みファイルを壊さず、各取得物にURL・取得時刻・ハッシュまたは応答メタデータを残す。

実データが十分なら、JSON・CSV・Markdownレポートに対象期間と件数が表示される。十分でなければ、成果物の `status=insufficient_data` と具体的な欠損理由を確認できる。どちらの場合も、合成データを混ぜた利益や「勝てる」といった結論は出さない。

## 設計上の決定

- New Yorkを最初の都市に固定した。市場ルールと観測所の対応を検証しやすく、都市追加時に共通スキーマを再利用できるためである。
- 実データを優先し、履歴予報が取得できない場合は停止理由を成果物にする。これは後日修正された予報による未来情報リークを避けるためである。
- 初回はWeather Onlyモデルを主結果にする。市場価格を入力にするモデルを混ぜると、気象情報の価値と市場価格の追随を区別できないためである。
- 実取引、APIキー、注文送信、少額運用は対象外とする。研究結果を検証する前に外部状態を変更しないためである。
